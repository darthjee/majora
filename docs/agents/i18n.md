# Frontend Internationalization (i18n)

## Overview

The frontend ships a lightweight, hand-rolled i18n layer instead of pulling in
a heavy framework — consistent with the project's existing style of small
custom utilities (`Router`, `GenericClient`, `AuthEvents`, etc.). Today only
English (`en`) is bundled, but the `Translator` API, language persistence,
and the header language selector are fully built out so adding a new
language is a drop-in change (see [Adding a new language](#adding-a-new-language)
below).

## Where translations live

Translation strings live in YAML files under `frontend/assets/i18n/`, one
directory per language, split into small per-namespace chunk files instead of
a single monolithic file:

```
frontend/assets/i18n/
  en/
    common.yaml          # header, modals, pagination, and other shared namespaces
    game_new_page.yaml
    treasure_edit_page.yaml
    ...
    index.js
  pt/
    common.yaml
    game_new_page.yaml
    treasure_edit_page.yaml
    ...
    index.js
```

`common.yaml` bundles every namespace shared by more than one page or by
cross-page reusable elements (`header`, the various modals, `pagination`,
`description_box`, `markdown_editor`, `language_selector`, etc.) as multiple
top-level YAML keys in one file. Every other, page-specific namespace gets its
own file named after the namespace (e.g. `game_new_page.yaml` holds the
`game_new_page:` key only).

Each language directory also has an `index.js` manifest — a small hand-written
file with three exports:

```js
import common from './common.yaml?raw';

const chunkLoaders = new Proxy({}, {
  get: (target, namespace) =>
    namespace in target ? target[namespace] : () => import(`./${namespace}.yaml?raw`),
});

const commonNamespaces = [
  'header',
  'login_modal',
  // ...every top-level namespace key bundled inside this language's `common.yaml`
];

export default common;
export { chunkLoaders, commonNamespaces };
```

- `common` (the default export) is the one genuine, always-bundled `?raw`
  import — no lazy thunk — since the header and other chrome elements need it
  available before the very first render (see [Lazy loading and
  `TranslationLoader`](#lazy-loading-and-translationloader) below).
- `chunkLoaders` is a `{ chunkName: () => import('./chunkName.yaml?raw') }`-shaped
  lookup — but rather than a hand-typed literal with one entry per
  page-specific namespace file, it's a `Proxy` around an (initially empty)
  plain object: its `get` trap computes `() => import('./${namespace}.yaml?raw')`
  on demand from the requested namespace name, by the same filename
  convention the hand-typed entries used to follow, so nothing needs to be
  enumerated up front. Vite only bundles statically-analyzable dynamic
  imports (no `import.meta.glob`, to keep the Node-based Jasmine test loader
  working — see [Adding a new language](#adding-a-new-language)); the
  template-literal `import()` call inside the trap is still
  statically-analyzable by Vite (same as `import(`./${name}.yaml?raw`)`
  patterns elsewhere), so chunk-splitting is unaffected. `target` stays a
  real, mutable object, so a real own-property set directly on `chunkLoaders`
  (as some specs do to inject a fake loader) is returned as-is instead of
  going through the computed fallback — the `namespace in target` check
  preserves that override seam.
- `commonNamespaces` is the hand-maintained list of top-level YAML keys
  bundled inside that language's `common.yaml` (`header`, the various
  modals, `pagination`, `description_box`, `markdown_editor`,
  `language_selector`, etc.) — kept in sync with `common.yaml`'s actual
  content whenever a shared namespace is added or removed. `en` and `pt`
  keep this list identical, mirroring the rest of the manifest's file layout.

Each chunk file is still bundled at build time via Vite's `?raw` import
suffix (no runtime fetch for `common`); `frontend/assets/js/i18n/TranslationLoader.js`
parses a chunk's raw YAML with [`js-yaml`](https://github.com/nodeca/js-yaml)
once its dynamic import resolves.

## The `namespace.key` convention

Keys are grouped under one top-level namespace per page or element, matching
the existing folder layout under `components/resources/<resource>/pages` and
`components/common`. For example:

```yaml
# common.yaml
header:
  title: Majora
  login: Login
login_modal:
  title: Login
  username_label: Username

# character_info.yaml
character_info:
  class_label: 'Class:'
  level_label: Level
```

This keeps keys easy to locate: if you're editing `HeaderHelper.jsx`, its
strings live under the `header:` namespace inside `common.yaml`. Each chunk
file keeps its namespace(s) as explicit top-level YAML keys — not inferred
from the filename — which matters for `common.yaml` bundling several
namespaces together, and stays consistent for the single-namespace files too.

## Lazy loading and `TranslationLoader`

Only the language active at startup pays for its `common` chunk eagerly.
Every other chunk — every page-specific namespace, for every language, plus
`common` itself for a language switched into later — loads lazily, on first
use, through `frontend/assets/js/i18n/TranslationLoader.js`.

`TranslationLoader` is a plain module-level singleton (no component
lifecycle, mirroring `LanguageStorage`/`LanguageEvents`) owning a permanent
in-memory cache keyed by `` `${language}:${namespace}` ``, each entry tracking
a `'loading' | 'loaded' | 'failed'` state:

- `request(language, namespace)` starts a chunk's dynamic import the first
  time it's asked for that pair — resolving `namespace` to either the
  language's `common` chunk (already resident) or its `chunkLoaders[namespace]`
  thunk — and is a no-op on any later call for the same pair, in any state.
  This is the dedupe: nothing needs to track in-flight requests separately,
  since the entry itself, once created, is the guard.
- `get(language, namespace)` returns the cached, parsed chunk once loaded, or
  `undefined` otherwise (not yet requested, still loading, or failed).
- On a successful resolve, the entry is parsed with `js-yaml` and cached
  permanently — entries are **never deleted or retried**, in any state. A
  dynamic `import()` can't be cancelled at the network level, so a chunk that
  started loading before a language switch keeps loading in the background
  regardless; letting it finish and cache silently (instead of tearing it
  down) avoids a duplicate fetch if the user switches back to that language
  later in the session.
- On a rejected import (e.g. a stale chunk URL after a deploy), the entry
  flips to `failed` instead of `loaded` — no retry, no crash. `Translator.t()`
  treats a `failed` entry exactly like one that's still loading: it returns
  the fallback.

There is **no explicit `loadNamespace()` call anywhere** — not at page mount
points, not anywhere else. Loading is triggered implicitly by `Translator.t()`
itself on a cache miss (see below), which is enough since components already
call `t()` for their own strings.

## Using `Translator.t()` in components

`frontend/assets/js/i18n/Translator.js` exposes a static `t(key, fallback)`
method that performs a dot-path lookup against the current language's chunk
data. The key's first dot-segment is its namespace (e.g. `header` for
`header.login`); `Translator` checks the current language's `commonNamespaces`
list to resolve that namespace to either the `common` chunk or a same-named
page-specific chunk, then looks it up via `TranslationLoader.get()`.

- **Cache hit** (the owning chunk is already loaded): the key resolves
  immediately, exactly like a synchronous lookup.
- **Cache miss**: `t()` fires `TranslationLoader.request()` for the owning
  chunk (fire-and-forget) and returns the fallback (or the key itself when no
  fallback is given) — the same fallback path already used for a missing or
  typo'd key, so a lazy load and an actual typo are visually indistinguishable
  until the load resolves. No crash, no blocking render, and **no call-site
  changes** anywhere across the ~97 namespaces' worth of `t()` calls: once the
  chunk resolves, `App.jsx`'s remount (triggered by `TranslationLoader`'s load
  event, see below) causes the same components to call `t()` again, which now
  hits the cache.

Only user-visible text is translated. `data-testid` attributes, console/log
messages, and code comments are left as-is.

> **Invariant:** `Translator.t()` must never be called with a key derived
> from user/data input. A namespace mapping to a nonexistent or unintended
> `.yaml` file now resolves through a live dynamic import (via the
> `chunkLoaders` `Proxy` described above) rather than a bounded object
> lookup. This risk is practically unchanged from before — a hand-typed
> `chunkLoaders` map never protected against arbitrary keys either — it's
> just worth stating explicitly now that the lookup is computed rather than
> a fixed literal.

## Language selector and persistence

`frontend/assets/js/components/common/misc/LanguageSelector.jsx` (+ its
`helpers/LanguageSelectorHelper.jsx` and
`controllers/LanguageSelectorController.js`, following the project's
Component/Helper/Controller trio convention) renders a dropdown in the
header showing a flag emoji and language code per registered language (e.g.
"🇬🇧 en"). Selecting an entry calls `Translator.setLanguage(code)`, which updates
the in-memory language, persists it via `LanguageStorage.js` (a thin
`localStorage` wrapper mirroring `AuthStorage.js`), and emits a
`language:changed` event via `LanguageEvents.js` (mirroring `AuthEvents.js`) so
the rest of the app can react. `Translator` reads the persisted language from
`LanguageStorage` on module load, so a page reload keeps the last choice.

`setLanguage()` does nothing beyond that — no explicit "reload the chunks the
current page needs for the new language" step. The remount described below
causes visible components to call `t()` again, which naturally re-triggers
`TranslationLoader` loads for whatever the new language needs, through the
same on-miss path used for a fresh page. Revisiting a language already fully
loaded this session (any chunk requested at least once) is instant — cache
hits included — since `TranslationLoader` never clears or re-fetches an
entry, even across repeated switches away and back.

`App.jsx` subscribes to both `LanguageEvents` and `TranslationEvents.js`
(`frontend/assets/js/i18n/TranslationEvents.js`, structured identically to
`LanguageEvents.js` but emitting a distinct `i18n:namespace-loaded` event) and
re-renders the page/element tree by including both the language and a
`TranslationEvents`-driven load counter in its remount `key`, without
requiring every component to individually subscribe to translation updates.
The two events stay distinct rather than one being reused for both purposes:
`TranslationLoader` emits `i18n:namespace-loaded` only when a chunk resolves
for the language that's *still* active at that moment (a load for a language
the user has since switched away from is cached silently, with no remount) —
and re-emitting `language:changed` with an unchanged language string wouldn't
trigger a React remount anyway, since a state setter bails out on an
identical primitive.

## Adding a new language

1. Add a new `frontend/assets/i18n/<code>/` directory (e.g. `pt/`) mirroring
   `en/`'s exact file set — the same `common.yaml` plus the same set of
   per-namespace `.yaml` files, each with the same keys as its `en/`
   counterpart — plus its own `index.js` manifest exporting `common`,
   `chunkLoaders`, and `commonNamespaces` (see [Where translations
   live](#where-translations-live) for the manifest's shape).
2. Import the new language's manifest in `Translator.js` (and
   `TranslationLoader.js`, which resolves chunk files independently) and
   register it in the `MANIFESTS` lookup table:
   ```js
   import * as pt from '../../i18n/pt/index.js';
   // ...
   const MANIFESTS = { en, pt };
   ```
3. Add a flag entry for the new code in
   `LanguageSelectorController`'s `FLAGS` table so it shows up correctly in
   the dropdown.

No other code changes are required — `Translator.getAvailableLanguages()`
and the selector automatically pick up the new entry. `frontend/scripts/check_i18n.js`
(run via `docker-compose run --rm majora_fe yarn check_i18n`) enforces that
every language directory has the exact same namespace-to-file mapping as the
others, so a forgotten or misnamed file for the new language fails loudly
instead of silently missing translations.
