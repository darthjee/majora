# Frontend Internationalization (i18n)

## Overview

The frontend ships a lightweight, hand-rolled i18n layer instead of pulling in
a heavy framework — consistent with the project's existing style of small
custom utilities (`Router`, `GenericClient`, `AuthEvents`, etc.). Today only
English (`en`) is bundled, but the `Translator` API, language persistence,
and the header language selector are fully built out so adding a new
language is a drop-in change (see [Adding a new language](#adding-a-new-language)
below).

## Where translations live

Translation strings live in YAML files under `frontend/assets/i18n/`, one
directory per language, split into small per-namespace chunk files instead of
a single monolithic file:

```
frontend/assets/i18n/
  en/
    common.yaml          # header, modals, pagination, and other shared namespaces
    game_new_page.yaml
    treasure_edit_page.yaml
    ...
    index.js
  pt/
    common.yaml
    game_new_page.yaml
    treasure_edit_page.yaml
    ...
    index.js
```

`common.yaml` bundles every namespace shared by more than one page or by
cross-page reusable elements (`header`, the various modals, `pagination`,
`description_box`, `markdown_editor`, `language_selector`, etc.) as multiple
top-level YAML keys in one file. Every other, page-specific namespace gets its
own file named after the namespace (e.g. `game_new_page.yaml` holds the
`game_new_page:` key only).

Each language directory also has an `index.js` manifest — a small hand-written
list of `?raw` imports, one per `.yaml` file in that directory, exported as a
`{ chunkName: rawYamlString }` map:

```js
import common from './common.yaml?raw';
import gameNewPage from './game_new_page.yaml?raw';
// ...one import per file in this directory, alphabetical

export default {
  common,
  game_new_page: gameNewPage,
  // ...
};
```

The manifest exists because Vite only bundles statically-analyzable imports
(no `import.meta.glob`, to keep the Node-based Jasmine test loader working —
see [Adding a new language](#adding-a-new-language)). Each chunk is bundled at
build time via Vite's `?raw` import suffix (no runtime fetch);
`frontend/assets/js/i18n/Translator.js` merges every chunk of a language's
manifest into one flat namespace map with
[`js-yaml`](https://github.com/nodeca/js-yaml) when first loaded.

## The `namespace.key` convention

Keys are grouped under one top-level namespace per page or element, matching
the existing folder layout under `components/resources/<resource>/pages` and
`components/common`. For example:

```yaml
# common.yaml
header:
  title: Majora
  login: Login
login_modal:
  title: Login
  username_label: Username

# character_info.yaml
character_info:
  class_label: 'Class:'
  level_label: Level
```

This keeps keys easy to locate: if you're editing `HeaderHelper.jsx`, its
strings live under the `header:` namespace inside `common.yaml`. Each chunk
file keeps its namespace(s) as explicit top-level YAML keys — not inferred
from the filename — which matters for `common.yaml` bundling several
namespaces together, and stays consistent for the single-namespace files too.

## Using `Translator.t()` in components

`frontend/assets/js/i18n/Translator.js` exposes a static `t(key, fallback)`
method that performs a dot-path lookup against the current language's map. If a
key is missing, it returns the fallback (or the key itself when no fallback is
given) instead of throwing — a typo in a key surfaces as visibly-wrong text in
the UI rather than crashing the render.

Only user-visible text is translated. `data-testid` attributes, console/log
messages, and code comments are left as-is.

## Language selector and persistence

`frontend/assets/js/components/common/misc/LanguageSelector.jsx` (+ its
`helpers/LanguageSelectorHelper.jsx` and
`controllers/LanguageSelectorController.js`, following the project's
Component/Helper/Controller trio convention) renders a dropdown in the
header showing a flag emoji and language code per registered language (e.g.
"🇬🇧 en"). Selecting an entry calls `Translator.setLanguage(code)`, which updates
the in-memory language, persists it via `LanguageStorage.js` (a thin
`localStorage` wrapper mirroring `AuthStorage.js`), and emits a
`language:changed` event via `LanguageEvents.js` (mirroring `AuthEvents.js`) so
the rest of the app can react. `Translator` reads the persisted language from
`LanguageStorage` on module load, so a page reload keeps the last choice.

`App.jsx` subscribes to `LanguageEvents` and re-renders the page/element tree
on a language change by including the language in its remount `key`, without
requiring every component to individually subscribe to translation updates.

## Adding a new language

1. Add a new `frontend/assets/i18n/<code>/` directory (e.g. `pt/`) mirroring
   `en/`'s exact file set — the same `common.yaml` plus the same set of
   per-namespace `.yaml` files, each with the same keys as its `en/`
   counterpart — plus its own `index.js` manifest listing a `?raw` import for
   every file in the directory (see [Where translations
   live](#where-translations-live) for the manifest's shape).
2. Import the new language's manifest in `Translator.js` and register it in
   the `TRANSLATIONS` lookup table:
   ```js
   import ptChunks from '../../i18n/pt/index.js';
   // ...
   const TRANSLATIONS = {
     en: mergeChunks(enChunks),
     pt: mergeChunks(ptChunks),
   };
   ```
3. Add a flag entry for the new code in
   `LanguageSelectorController`'s `FLAGS` table so it shows up correctly in
   the dropdown.

No other code changes are required — `Translator.getAvailableLanguages()`
and the selector automatically pick up the new entry. `frontend/scripts/check_i18n.js`
(run via `docker-compose run --rm majora_fe yarn check_i18n`) enforces that
every language directory has the exact same namespace-to-file mapping as the
others, so a forgotten or misnamed file for the new language fails loudly
instead of silently missing translations.
