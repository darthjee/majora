# Plan: Add stl search system

Issue: [1017-add-stl-search-system.md](../issues/1017-add-stl-search-system.md)

## Overview

Add a new standalone top-level Django app, `miniatures`, that catalogs STL 3D-printable files
(mostly game miniatures) Majora only links to, never hosts. This first pass adds the core
entities (`StlModel`, `StlModelLink`, `StlModelPhoto`, `Source`, `Tag`) and two read-only,
authenticated, paginated endpoints (`GET /miniatures.json`, `GET /miniatures/<id>.json`), reusing
existing patterns (`BaseLink`, `BasePhoto`, the display-photo FK pattern, the shared `Paginator`)
instead of inventing new ones.

## Context

- No dedicated STL/miniature catalog exists today — only the generic `link_type='stl'` choice on
  `games.BaseLink`.
- The catalog is intentionally cross-domain (available in every domain, unlike `Game`) and has no
  game relationship — so it has no dependency on the still-unmerged domain-extraction issue #1015.
- Only `list`/`show` endpoints ship in this issue; no create/update/delete, and no search/filter
  query params despite the issue title (deferred to a follow-up issue).
- `Source`/`Tag` are global, deduplicated lookup tables (unique `name`), managed via Django admin
  for now since there are no write endpoints yet.

## Implementation Steps

### Step 1 — App skeleton

Create `backend/miniatures/` mirroring the shape of `backend/accounts/` (the simplest existing
multi-resource app): `apps.py` (`MiniaturesConfig`, `default_auto_field =
'django.db.models.BigAutoField'`, `name = 'miniatures'`), `models/`, `serializers/`, `views/`,
`urls/`, `admin.py`, `migrations/`, `tests/` (mirroring the same tree). Add `'miniatures'` to
`INSTALLED_APPS` in `backend/majora_project/urls.py`'s sibling `backend/majora_project/settings.py`
(after `'conversations'`).

### Step 2 — Models (`miniatures/models/`)

All five models declare `history = HistoricalRecords(app='versioning', user_db_constraint=False,
...)`, matching every other model in the codebase (`Game`, `Character`, `GameLink`, `GamePhoto`).

- `Source` (`miniatures/models/source.py`) — `name = models.CharField(max_length=200, unique=True)`.
- `Tag` (`miniatures/models/tag.py`) — `name = models.CharField(max_length=200, unique=True)`.
- `StlModel` (`miniatures/models/stl_model.py`) —
  - `name = models.CharField(max_length=200)`
  - `photo = models.ForeignKey('miniatures.StlModelPhoto', on_delete=models.SET_NULL, null=True, blank=True, related_name='+')`
    (same nullable-FK-to-own-photo pattern as `Character.photo`)
  - `sources = models.ManyToManyField('miniatures.Source', related_name='stl_models', blank=True)`
  - `tags = models.ManyToManyField('miniatures.Tag', related_name='stl_models', blank=True)`
- `StlModelLink` (`miniatures/models/stl_model_link.py`) — extends
  `games.models.base_link.BaseLink` as-is (`text`, `url`, `link_type` choices; `BaseLink` already
  declares its own `history`), plus `stl_model = models.ForeignKey(StlModel,
  on_delete=models.CASCADE, related_name='links')`.
- `StlModelPhoto` (`miniatures/models/stl_model_photo.py`) — extends
  `games.models.base_photo.BasePhoto` as-is (`path`, `ready`; already declares its own `history`),
  plus `stl_model = models.ForeignKey(StlModel, on_delete=models.CASCADE,
  related_name='photos')`.

Cross-app import note: `miniatures` depends on `games` only for the two abstract base classes
(`BaseLink`, `BasePhoto`) — no other coupling. Acceptable per the issue's own decision; extracting
those into a shared/common module is explicitly out of scope here.

`miniatures/models/__init__.py` re-exports all five classes by name, mirroring
`games/models/__init__.py`'s stable re-export convention.

### Step 3 — Migrations

Generate the initial `miniatures` migration (`0001_initial`) via `makemigrations` inside the
`majora_tests`/`majora_be` container. No backfill needed — brand-new tables. Note the `versioning`
app also needs a migration for the five new `Historical*` models (auto-generated by
`simple_history`'s `HistoricalRecords`), same as any other new tracked model.

### Step 4 — Admin (`miniatures/admin.py`)

Register all five models (`StlModel`, `StlModelLink`, `StlModelPhoto`, `Source`, `Tag`), mirroring
`games/admin.py`'s flat `admin.site.register(...)` style. This is the only management surface for
`Source`/`Tag` (and for creating `StlModel`/links/photos) until write endpoints exist.

### Step 5 — Serializers (`miniatures/serializers/`)

- `SourceSerializer` — `fields = ['name']` (no `id` — the issue's show payload lists sources as
  `{name}` only).
- `StlModelLinkSerializer` — `fields = ['id', 'text', 'url', 'link_type']`, mirroring
  `GameLinkSerializer` exactly (`games/serializers/games/game_link.py`).
- `StlModelListSerializer` — `photo_url = serializers.CharField(source='photo.path',
  default=None, read_only=True)`; `fields = ['id', 'name', 'photo_url']`.
- `StlModelDetailSerializer` — same `photo_url`, plus `links = StlModelLinkSerializer(many=True,
  read_only=True)`, `sources = SourceSerializer(many=True, read_only=True)`, `tags =
  serializers.SlugRelatedField(many=True, slug_field='name', read_only=True)` (flat array of
  strings, per the issue's spec); `fields = ['id', 'name', 'photo_url', 'links', 'sources',
  'tags']`.

`miniatures/serializers/__init__.py` re-exports all four, mirroring
`games/serializers/__init__.py`.

### Step 6 — Views & URLs

`miniatures/views/stl_models_list.py` and `miniatures/views/stl_model_detail.py`, following the
`IsAuthenticated` + paginated pattern already used by
`accounts/views/authorization_requests/list.py` (not the `AllowAny` pattern used by
`games/views/treasures/*.py` — this catalog requires login):

```python
@api_view(['GET'])
@permission_classes([IsAuthenticated])
def stl_models_list(request):
    page, headers = Paginator(request, StlModel.objects.all()).paginate()
    serializer = StlModelListSerializer(page, many=True)
    return skip_cache(Response(serializer.data, headers=headers))
```

`CookieTokenAuthentication` doesn't need an explicit `authentication_classes` decorator — it's
already `DEFAULT_AUTHENTICATION_CLASSES` in `majora_project/settings.py`'s `REST_FRAMEWORK`
config, same as `accounts/views/authorization_requests/list.py`.

**`X-Skip-Cache: true` is required on both responses** — not optional. Per
`docs/agents/access-control/principles.md`'s `X-Skip-Cache` rule, any endpoint not open to
`AllowAny` always sets this header; since these endpoints require login, they're non-`AllowAny`
by definition. Add a small `skip_cache(response)` helper to `miniatures/views/`, mirroring
`accounts/views/authorization_requests/_shared.py`'s one-liner (`response['X-Skip-Cache'] =
'true'`).

`stl_model_detail` returns 404 (`{'errors': {'detail': ['not found']}}`, status 404) for an
unknown `id`, matching `treasure_detail`'s not-found shape.

`miniatures/urls/__init__.py` declares:
```python
urlpatterns = [
    path('miniatures.json', views.stl_models_list, name='miniatures-list'),
    path('miniatures/<int:stl_model_id>.json', views.stl_model_detail, name='miniatures-detail'),
]
```
Included from `majora_project/urls.py` alongside `games.urls`/`accounts.urls`:
`path('', include('miniatures.urls'))`.

### Step 7 — Access-control documentation

Add `docs/agents/access-control/stl-model.md` documenting both endpoints as **IsAuthenticated**
(no `AllowAny` regular form, unlike the Game/Treasure "regular" category — this is a new,
fifth resource shape: a shared, cross-domain, login-only catalog with no game/staff/account
category fit), and explicitly note the `X-Skip-Cache: true` requirement from Step 6 as the
deviation callout `principles.md` asks for. List exposed fields per endpoint (matching Step 5).
Add a line for it under `docs/agents/access-control.md`'s "Models / resources" contents list.

### Step 8 — Pagination convention documentation

Add the already-agreed convention note to `docs/agents/pagination.md`'s `## Overview` section:
all new list endpoints must use the shared `Paginator`; existing unpaginated endpoints are not
retrofitted as a side effect of unrelated work. (This was drafted and reverted during the
`discuss-issue` dialogue for this issue, to be applied here instead.)

### Step 9 — Tests (`miniatures/tests/`)

Mirror `backend/games/tests/` conventions (`pytest.mark.django_db`, `setup_method` fixtures, one
test file per model/serializer/view file, `<module>_test.py` naming):
- `tests/models/` — one file per model (uniqueness constraints on `Source`/`Tag`, `StlModel`
  M2M/FK behavior, `on_delete=SET_NULL` for `photo`, `on_delete=CASCADE` for links/photos).
- `tests/serializers/` — list/detail field shapes, `photo_url` resolving `None` when no photo
  set, `tags` as a flat string array, `sources` as `{name}` objects.
- `tests/views/` — pagination headers on list, 401 for unauthenticated requests on both
  endpoints, 404 on unknown detail id, `X-Skip-Cache: true` present on both responses.
- `tests/admin_test.py` (or equivalent) — all five models registered.

## Notes

- **No `cache`/Navi work in this issue.** `docs/agents/cache-warmer.md` explicitly excludes
  restricted (non-`AllowAny`) endpoints from `navi/navi_config.yaml`'s warm-up chain, except when
  the same URL also serves a regular `AllowAny` form (e.g. `/games.json`) — neither
  `/miniatures.json` nor `/miniatures/<id>.json` has one, so both are excluded outright, not
  added to `navi/resources/`.
- **No `data-access`/`security`/`product-owner` implementation work.** These are read-only
  reviewer agents (per `.claude/agents/`) — they review the diff at fix/PR time, they don't own
  plan steps.
- **No `frontend`/`proxy`/`infra`/`translator` work** — this issue is API-surface-only, no UI, no
  proxy rule, no deployment, no user-facing strings.
- This plan intentionally has no agent split (`AGENT_SPLIT=false`): only `backend`-shaped work
  plus a few `docs/` files (access-control, pagination) has any real content, and per this repo's
  convention an unsplit plan is implemented directly by the architect, so the docs/ edits above
  are not out of scope despite living outside `backend/`.
