# Backend Plan: Improve miniature/stl_model

Main plan: [plan.md](plan.md)

## Shared contracts

Produces the API surface described in [plan.md](plan.md)'s "Shared contracts" section: `StlModel` gains `url`/`size` and exposes `races`/`roles` (arrays) instead of the current singular `race`/`role`, on the create/update/detail serializers only — the list serializer is untouched.

## Implementation Steps

### Step 1 — Grow `RACE_CHOICES` and add `SIZE_CHOICES`

In `backend/miniatures/models/stl_model.py`:
- Append the 18 new race constants/choices (Turtlefolk, Cthulhufolk, Humanoid, Construct, Monstrosity, Undead, Aberration, Beast, Alien, Fiend, Fey, Giant, Dragon, Celestial, Elemental, Cyborg, Plant, Ooze) to `RACE_CHOICES`, after the existing 11 — order matters, it must match `RACE_VALUES` in `frontend/assets/js/components/resources/stl_model/stlModelEnums.js` exactly (same contract already documented there for `TYPE_VALUES`/`RACE_VALUES`/`ROLE_VALUES`).
- Add `SIZE_TINY`/`SIZE_SMALL`/`SIZE_MEDIUM`/`SIZE_HUGE`/`SIZE_GARGANTUAN`/`SIZE_LIFE` constants and `SIZE_CHOICES`, same style as `TYPE_CHOICES`.

### Step 2 — Add `url` and `size` fields, drop `race`/`role`

Still in `stl_model.py`:
- Add `url = models.URLField(max_length=200, unique=True, null=True, blank=True, default=None, validators=[URLValidator(schemes=['http', 'https'])])` — mirrors `Collection.url`'s `unique=True`/`null=True`/`blank=True`/`default=None` shape (see that model's comment explaining why `default=None` is required under `unique=True`), plus the scheme-restricted validator (a hardening `Collection.url` itself doesn't have — retrofitting that is #1108, out of scope here).
- Add `size = models.CharField(max_length=16, choices=SIZE_CHOICES, null=True, blank=True)` — optional, matching `race`/`role`'s current nullability, not required like `type`.
- Remove the `race`/`role` `CharField`s themselves (their choice lists move to the new join models below).

### Step 3 — New `StlModelRace`/`StlModelRole` join models

New files, following the flat one-model-per-file convention already used in `backend/miniatures/models/` (e.g. `stl_model_link.py`):

- `backend/miniatures/models/stl_model_race.py` — `StlModelRace(models.Model)`:
  - `stl_model = models.ForeignKey('miniatures.StlModel', on_delete=models.CASCADE, related_name='races')`
  - `creature = models.CharField(max_length=16, choices=StlModel.RACE_CHOICES)`
  - `class Meta: unique_together = [('stl_model', 'creature')]` (list-of-tuple form, matching `conversations/models/conversation_participant.py`'s convention)
  - No `HistoricalRecords` — matches `StlModelLink`'s precedent (child/join models under `StlModel` aren't individually historied; only top-level named entities are).
- `backend/miniatures/models/stl_model_role.py` — `StlModelRole(models.Model)`, identical shape: `stl_model` FK (`related_name='roles'`), `role = models.CharField(max_length=16, choices=StlModel.ROLE_CHOICES)`, `unique_together = [('stl_model', 'role')]`, no history.

Register both in `backend/miniatures/models/__init__.py`'s imports and `__all__`.

### Step 4 — Migrations

Two migrations in `backend/miniatures/migrations/` (numbered after `0004_...`), in this order (data must move before the old columns are dropped):

1. **Schema** (`0005_...`): `AddField(url)`, `AddField(size)` on `StlModel`; `CreateModel(StlModelRace)`, `CreateModel(StlModelRole)` — both with the full grown choice lists from Step 1. Leaves the old `race`/`role` columns on `StlModel` untouched for now.
2. **Data + column drop** (`0006_...`): a `RunPython` step that, for every `StlModel` with a non-null `race`/`role`, creates the corresponding `StlModelRace`/`StlModelRole` row, followed by `RemoveField(race)`/`RemoveField(role)` on `StlModel` in the same migration (operations run in the order listed, so the copy happens first).

Mirror the equivalent changes in `backend/versioning/migrations/` for `HistoricalStlModel` (`AddField(url)`, `AddField(size)`, `RemoveField(race)`, `RemoveField(role)`) — per the issue's edge-case decision, historical `race`/`role` data is dropped, not migrated, so no `RunPython` step is needed there. Easiest to get right by running `manage.py makemigrations` inside the dev container after Steps 1-3 and reviewing/splitting the autogenerated output to match the two-migration sequence above; do the same for `versioning`.

### Step 5 — Sync helper for races/roles

New file `backend/miniatures/serializers/_stl_model_races_roles_sync.py` (leading underscore, matching `_tags_sync.py`'s convention — an internal helper, not re-exported via `serializers/__init__.py`):
- `RacesSync`/`RolesSync` classes, each constructed with `(stl_model, values)` and an `.apply()` method that, wrapped in `transaction.atomic()` (same reasoning as `TagsSync`), creates one `StlModelRace`/`StlModelRole` row per de-duplicated entry in `values`. No get-or-create needed (unlike `TagsSync`) since these aren't free-typed — validity against the choice list is enforced at the serializer field level (Step 6), and de-duplication in Python avoids tripping the `unique_together` constraint on a payload containing the same value twice.
- On update (PATCH), the equivalent of "replace the set": delete the stl_model's existing `StlModelRace`/`StlModelRole` rows and re-`apply()` the new list — simplest correct semantics for a full-replacement array field, mirroring how `sources`/`collections` use `.set()` on create (there's no true M2M `.set()` here since this isn't a real M2M, so the serializer's `update()` does the delete+recreate explicitly).

### Step 6 — Serializer changes

- `backend/miniatures/serializers/stl_model_create.py`: replace `race`/`role` in `Meta.fields` with `url`, `size`, `races`, `roles`. Add `races = serializers.ListField(child=serializers.ChoiceField(choices=StlModel.RACE_CHOICES), required=False, default=list)` and the equivalent `roles` field. `create()` pops `races`/`roles` from `validated_data` and calls `RacesSync(stl_model, races).apply()` / `RolesSync(...)`, alongside the existing `tags`/`sources`/`collections` handling.
- `backend/miniatures/serializers/stl_model_update.py`: `Meta.fields` becomes `['name', 'owned', 'type', 'url', 'size', 'races', 'roles']` (still excludes `photo`/`tags`/`sources`/`collections`, unchanged reasoning). Add an `update()` override doing the delete-and-resync described in Step 5 for `races`/`roles` when present in the payload; scalar fields (`name`/`owned`/`type`/`url`/`size`) update via the default `ModelSerializer.update()` behavior.
- `backend/miniatures/serializers/stl_model_detail.py`: add `url`, `size` (plain passthrough fields) and `races`/`roles` — `serializers.SlugRelatedField(many=True, slug_field='creature', source='races', read_only=True)` and the `role`/`roles` equivalent, mirroring how `tags` is exposed today (`SlugRelatedField(many=True, slug_field='name', ...)`), returning e.g. `["elf", "dragon"]`.
- `backend/miniatures/serializers/stl_model_list.py`: **no change** — stays `['id', 'name', 'photo_url']`.

### Step 7 — Validation

- `url`: rely on the model's `URLField` + `URLValidator(schemes=['http', 'https'])` from Step 2 to reject non-http(s) schemes (e.g. `javascript:`) at the model-validation layer; confirm `full_clean()`/serializer validation actually triggers it (DRF's `ModelSerializer` runs model field validators by default for `URLField`-backed serializer fields).
- `races`/`roles`: `ChoiceField` already rejects out-of-list values with a 400; no extra validation needed for that. Consider whether an over-long list needs a cap similar to `MAX_TAGS` — given both constant lists are small (29/13) and duplicates are already deduplicated, a cap isn't strictly necessary, but flag this as a judgment call for whoever implements if it seems warranted.
